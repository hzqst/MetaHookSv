# Game-private symbols used by `metahook.cpp`

This document inventories the unexported private functions, private data slots, and private call sites that `src/metahook.cpp` locates in the game engine image and consumes in subsequent logic in the current version. Symbol names use the locally held variables in the code; names in parentheses indicate inferred game-side meanings based on use, rather than official debug-symbol names from the upstream binary.

> **gamedata migration status (2026-08-30)**: The following ten "final-consumer" symbols are now resolved from the local gamedata catalog through `ResolveGameSymbol`, rather than through mirror-image plus signature/string/cross-reference scans:
> `build_number`, `Sys_Error`, `ClientDLL_HudInit`, `cl_enginefuncs`, `cl_funcs`, `g_phClientModule`, `g_pClientFactory`, `videomode`, `gClientUserMsgs`, `cl_parsefuncs`.
> The resolution entry point is `MH_LoadEngine_ResolveSymbol` in `src/metahook.cpp`; catalog initialization, module-source registration, and mirror-alias registration are the `GameData::Initialize` / `RegisterModuleFileSource` / `RegisterMirrorAlias` calls in `MH_LoadEngine`.
> `ResolveGameSymbol` always returns `moduleBase + rva`. The RVAs for both `cl_enginefuncs` and `cl_funcs` denote the embedded global object itself; only when intercepting `ClientDLL_Init`'s indirect call to `cl_funcs.pInitFunc` does `MH_LoadEngine_ResolveGlobalOperand` use that record's `signatureRva + instructionOffset + operandOffset` to compute the machine-instruction operand address.
>
> The cvar branch (`cvar_hooks` / `Cvar_Set` / `Cvar_DirectSet`) and the blob client's `FreeBlob` still use legacy scanning because the release gamedata does not yet contain these symbols (`scripts/validate-gamedata.py` blocks releases as a gate). The table below still primarily describes legacy location methods and will be updated when the data is complete.

## Scope and shared resolution process

- The scope includes game-internal objects whose addresses are stored in global/local variables or used as disassembly starting points, comparison targets, or hook/patch targets.
- It excludes MetaHook's own symbols such as `MH_*`, local state such as `g_ManagedCvarCallbackList`, and APIs obtained from the public `cl_enginefunc_t` table (for example, `Cvar_Set` and `GetFirstCmdFunctionHandle`).
- Most resolution occurs in the mirror image `DllInfo` (preferentially using `g_hMirrorEngine`), then maps back to the actually loaded image `RealDllInfo` by RVA through `ConvertDllInfoSpace`; the conversion implementation is at `src/metahook.cpp:1268-1279`, and the dispatch of all resolution routines is at `src/metahook.cpp:2265-2276`.
- A resolution failure aborts loading through `MH_SysError`; therefore, every required item in the table below has a runtime gate. The variables are also cleared by `MH_ResetAllVars` (`src/metahook.cpp:1211-1241`).

## Objects derived from private slots but not independently scanned

- `g_pExportFuncs` directly points to `cl_funcs`; it is not produced by a second dereference from a machine-instruction operand. After the engine populates client exports, `ClientDLL_Initialize` copies it, passes it to plugins, and calls the original `Initialize`.
- `gMetaSave.pEngineFuncs` is copied from direct-global `cl_enginefuncs` and then used as the public `cl_enginefunc_t` table. Therefore, `Cmd_GetCmdBase` is still not an independently resolved private function.
